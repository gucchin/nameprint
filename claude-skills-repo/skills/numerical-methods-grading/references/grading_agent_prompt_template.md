# 学生別採点サブエージェント プロンプトテンプレート

38人分など多数の学生を1人で順番に読んで採点すると、コンテキストを圧迫し遅くなる。
代わりに、`Agent` ツール(サブエージェント)を学生1人につき1体ずつ立ち上げ、並列に採点させる。
1回のアシスタントターンの中で複数の `Agent` 呼び出しを同時に発行すること(並列実行される)。

Workflowツール(`ultracode`)は使わない — ユーザーが明示的に「ワークフローを使って」と言わない限り、
通常の `Agent` ツールのファンアウトで十分であり、これが今までの採点でも使われてきた方法。

## なぜ1人1エージェントか

- 各エージェントのコンテキストを、その学生の提出物と採点基準だけに保つことで、他の学生の答案に
  引きずられた採点(アンカリング)を防げる。
- 手書きPDF/スキャン画像、docx、pythonコードなど提出形式がバラバラでも、エージェントが
  `Read`(PDF/画像を直接見る)や `pandoc -t markdown`(docx読み取り)を使い分けて対応できる。
- 採点者向けの参考として、必要であれば計算検証(例: `python3` でコードを実際に実行してみる、
  `pdfimages` でPDFに図が本当に埋め込まれているか確認する)までエージェントにやらせられる。

## プロンプトの組み立て方

各サブエージェントへのプロンプトは、それ単体で完結していること(会話の文脈を一切前提にしない)。
最低限、次の要素を含める:

1. **課題の内容**: 課題PDFから抽出した問題文(演習1、演習2、…)。
2. **採点基準**: 承認済みの採点基準docx(`build_rubric_docx.js` で作成したもの)に基づく、
   演習ごと・小問ごとの配点と評価観点。模範解答の値があれば含める。
3. **提出物のファイルパス**: この学生の提出フォルダ内の実ファイルへの絶対パス
   (`/mnt/user-data/uploads/...` 配下。フォルダ構成は下記「提出フォルダの探し方」参照)。
4. **出力フォーマットの指定**: 下記のJSON形式で、最後にJSONオブジェクトのみを出力するよう
   明示的に指示する。前置きの説明文やコードフェンス(```)は付けないよう指示すること
   (パースしやすくするため)。

### 出力JSONスキーマ

```json
{
  "participant_id": "31356828",
  "name": "SONODA, Naohiro 園田尚弘",
  "exercises": [
    {"name": "演習1", "score": 18, "max": 21, "subscores": [6, 6, 6]},
    {"name": "演習2", "score": 6, "max": 29, "subscores": [4, 0, 2]}
  ],
  "content_score": 24,
  "content_max": 50,
  "note": "演習2②実質白紙。ファイル名は第3回課題名だが中身は本課題と一致(PDF確認済み)。",
  "flag": "要学生確認"
}
```

- `content_score` は演習の合計と一致させる(検算はこちらで行う)。
- `flag` は `"要学生確認"` または `null`。**`flag` が付いた学生は、`update_csv.py` によって
  Moodleの採点ワークフローステータスが「採点中」(未確定)のままになる**ので、本当に人間の
  追加確認が必要なケースにだけ付けること。例: 提出物が明らかに途中で切れている、ページ数が
  合わない、内容が課題と食い違っている、など「採点者の判断だけでは確定できない」場合。
  一見怪しく見えたが自分(採点エージェント)で確認して問題なしと判断できたケース
  (例: ファイル名は別回のものだが中身を読んで本課題の内容と一致すると確認できた)は、
  `flag` は `null` のままにし、確認した経緯を `note` に書く — この場合は既に解決済みなので
  「採点完了」で構わない。
- `note` は自由記述。空文字より `null`/省略の方が扱いやすい。

過去の運用では自由形式のMarkdown行(正規表現でパース)を使っていたが、記法の揺れで
パース漏れが起きたことがある(例: 満点の学生に "(満点)" のような注記が付いて正規表現が
マッチしなかった)。JSON形式に統一することでこの種の脆さを避けられる。

### 集約方法

各サブエージェントの返答(最終テキスト)を `json.loads()` でパースし、`participant_id` を
キーにしたリスト/辞書にまとめる。パースに失敗したエージェントがいたら、そのエージェントだけ
再実行するか、手動でJSONを修復する(コンテキストが軽いので再実行が簡単)。

集約結果は `compute_grades.py` の入力(`grading_input.json`)の `students` フィールドに変換し、
また `build_summary_docx.js` の入力(`report_data.json`)の演習別内訳・特記事項としても使う。

## 提出フォルダの探し方 (Moodle形式)

```
<課題フォルダ>/<氏名 参加者ID>_assignsubmission_file/<提出ファイル>
```

例: `数値計算法(2026260402400101)-第8回課題-6109428/園田尚弘_31356828_assignsubmission_file/repo1.pdf`

フォルダ名の末尾の数字が、成績CSVの `ID` 列 `参加者XXXXX` の数字部分と対応する。この数字を
学生の一意キー(`participant_id`)として使うと、CSVとの突き合わせがずれない。

ユーザーのWindows機からファイルをステージングする際、日本語の氏名部分でUnicodeの字体違い
(例: 「高」と「髙」、「恒」と「恆」)により `device_stage_files` が「存在しない」エラーを返す
ことがある。エラーが出たら、まず `device_list_dir` で該当フォルダの中身を直接列挙して正確な
文字を確認し、必要なら Python の `ord()`/`hex()` で目視確認してから再試行する。
